# English2 产品总需求文档

**项目名称：** English2
**项目类型：** 个人 / 家庭英语学习 Web 应用
**核心内容：** 中国硕士研究生入学考试英语（二）历年真题学习系统
**当前真题范围：** 2010–2026，共 17 套
**文档性质：** 产品最高层级需求文档
**适用对象：** 产品设计、前端、后端、数据处理、AI Coding Agent
**状态：** 基础产品需求已确定，后续功能持续演进

---

# 1. 产品定位

## 1.1 产品是什么

English2 是一个以 **英语（二）历年真题** 为核心内容的个人英语学习系统。

它不是简单的“真题题库网站”，而是逐步构建成为一个围绕真实考试内容形成完整学习闭环的学习工具：

```text
历年真题
    ↓
试卷
    ↓
Section
    ↓
具体题目
    ↓
做题
    ↓
查看结果
    ↓
理解答案
    ↓
记录学习行为
    ↓
错题 / 历史 / 复习
    ↓
长期重复学习
```

产品最终目标不是单纯展示题目，而是让用户能够持续使用历年真题完成：

**练习 → 理解 → 复习 → 再练习**

---

# 2. 产品核心目标

English2 的核心目标按照优先级分为以下几层。

## 2.1 第一目标：完整、准确地承载历年真题

系统必须能够稳定保存并展示：

* 2010–2026 年英语（二）真题
* 每套试卷
* 每个 Section
* 每一道题
* 每个选项
* 必要的题目内容
* 必要的答案与解析
* 必要的文章、提示及辅助信息

数据必须保持结构化，而不是依赖一堆页面专用 JSON。

---

## 2.2 第二目标：让用户方便地学习真题

用户应该能够非常自然地完成：

```text
进入 English2
↓
选择年份
↓
进入该套真题
↓
选择 Section
↓
开始练习
↓
完成题目
↓
查看结果 / 答案 / 解析
```

整个过程应尽可能少产生无意义的页面跳转和操作。

---

## 2.3 第三目标：逐步建立长期学习系统

在基础真题系统稳定之后，逐步增加：

* 做题记录
* 学习历史
* 错题
* 收藏
* 重做
* 学习统计
* 阶段性复习
* 其他有实际学习价值的功能

这些功能必须建立在已经稳定的真题和练习系统之上。

---

# 3. 产品使用对象

## 3.1 当前使用范围

English2 当前定位为：

**个人 / 家庭内部使用的学习工具。**

不是商业化 SaaS。

因此：

* 不以大规模多租户架构为目标
* 不为了理论上的极端安全场景过度设计
* 不引入没有实际价值的复杂基础设施
* 不为了未来商业化而提前堆砌系统复杂度

---

## 3.2 用户体验原则

即使只有少量用户，产品也应保持良好的：

* 信息层级
* 页面结构
* 操作逻辑
* 响应速度
* 移动端体验
* 错误处理
* 数据一致性

目标是：

> **小而完整，而不是大而复杂。**

---

# 4. 产品核心原则

## 4.1 真题优先

历年真题是整个产品的核心资产。

任何新功能都不应破坏真题数据结构。

---

## 4.2 数据库是运行时事实来源

运行中的前端数据应以 Supabase 数据库为主要事实来源。

核心关系：

```text
exam_papers
    ↓
exam_sections
    ↓
section_items
    ↓
item_options
```

即：

```text
Paper
  └── Section
        └── Item
              └── Option
```

---

## 4.3 不建立重复的运行时数据源

不要为了方便前端展示，再建立一个与数据库重复的：

* paper index
* paper list JSON
* runtime exam catalog JSON

例如：

`data/exams/index.json`

目前属于**离线数据处理 / 审计产物**，不是运行时 Paper List 数据源。

同样：

`data/exams/manifest.json`

属于离线同步、指纹和数据审计相关产物，不是前端运行时数据源。

---

## 4.4 简单优先

English2 不追求复杂架构。

当存在：

```text
简单方案
vs
复杂但理论上更完美的方案
```

如果简单方案已经满足实际产品要求，应优先使用简单方案。

---

## 4.5 不过度工程化

不为了以下原因提前增加复杂系统：

* 理论上的百万用户
* 理论上的极端攻击
* 理论上的多租户
* 理论上的微服务
* 理论上的高并发
* 理论上的复杂权限模型

产品需求没有要求时，不主动增加。

---

# 5. 真题数据体系

## 5.1 当前真题范围

当前正式真题范围：

```text
2010
2011
2012
...
2025
2026
```

共：

**17 套**

当前每一年对应一套正式 Paper。

---

## 5.2 Paper 层

Paper 是用户理解中的：

> “某一年英语（二）完整真题”

例如：

```text
英语（二）2026 年真题
英语（二）2025 年真题
英语（二）2024 年真题
...
英语（二）2010 年真题
```

数据库：

`exam_papers`

主要业务字段：

* `id`
* `year`
* `title`
* `is_current`

Paper 层负责表达：

**“这是哪一年的哪一套考试。”**

---

## 5.3 Section 层

一套 Paper 包含多个 Section。

数据库：

`exam_sections`

Section 负责表达：

**“这一套真题中的一个考试部分。”**

Section 可以包含：

* 标题
* 类型
* 时间
* 分值
* passage
* prompt
* tips
* 其他必要信息

---

## 5.4 Item 层

数据库：

`section_items`

每一个 Item 对应一道具体题目。

主要包括：

* 题号
* 题目内容
* 类型
* 所属 Section

---

## 5.5 Option 层

数据库：

`item_options`

负责保存题目的选项。

例如：

```text
A. ...
B. ...
C. ...
D. ...
```

---

```text
Supabase
```

```text

↓
```

```text
↓
正确答案
↓
解析
↓
理解
```

---

## 12.1 答案边界

答案和内部解析数据不能无条件暴露给前端。

当前已经建立基本答案边界。

需要继续遵循：

> 用户需要看到的学习信息可以提供；不需要暴露的内部字段不应该成为普通前端读取数据。

---

## 12.2 中文参考

`passage_zh` 不属于当前前端运行时需要展示的核心数据。

当前产品不依赖它完成正常 Paper → Section → Practice 流程。

因此：

* 数据可以保留
* 前端不依赖
* 不把它重新引入正常学习流程

# 13. 学习闭环

```text
发现真题
    ↓
选择年份
    ↓
选择 Section
    ↓
开始做题
    ↓
提交答案
    ↓
查看结果
    ↓
查看答案
    ↓
查看解析
    ↓
理解错误
    ↓
记录学习
    ↓
以后重新复习
```

未来进一步形成：

```text
做题
 ↓
错题
 ↓
复习
 ↓
重做
 ↓
掌握
```

# 14. 错题系统

错题系统属于后续阶段，不是当前最基础真题展示功能的前置条件。

未来应该能够记录：

```text
Paper
Section
Item
用户答案
正确答案
作答时间
作答次数
```

然后形成：

**我的错题**

---

## 14.1 错题目标

用户可以：

* 查看错题
* 重新做题
* 查看解析
* 标记已掌握
* 重复复习

具体数据模型以后根据真实学习流程设计。

不要为了“可能需要”提前复杂化。

---

# 15. 学习历史

未来支持：

```text
最近做过什么
哪套真题做过
哪个 Section 做过
哪些题做过
正确率
完成时间
```

目标不是做复杂 BI 系统。

目标是：

> 帮助用户知道自己学过什么、哪里薄弱。

---

# 16. 学习统计

未来可以逐步增加：

* Paper 完成情况
* Section 完成情况
* 正确率
* 错题数量
* 学习次数
* 连续学习情况

但统计功能必须建立在真实学习行为数据之上。

不提前设计大量没有数据支撑的图表。

---

# 17. 用户系统

English2 可以使用 Supabase Auth。

当前产品定位下：

* 不需要复杂的组织系统
* 不需要企业账号
* 不需要 RBAC 大型权限体系
* 不需要多租户架构

用户系统的主要目的：

**识别学习用户并保存其学习数据。**

---

# 18. 数据权限原则

安全目标：

**够用的安全，而不是无限收紧。**

重点保护：

* 正确答案
* 答案解析
* 内部数据
* 不需要暴露给前端的字段

同时避免：

* 为普通业务字段增加无意义复杂权限
* 为理论攻击场景建立复杂架构
* 为两个用户设计商业 SaaS 级权限系统

---

# 19. 数据库设计原则

数据库结构应该保持：

```text
exam_papers
    ↓
exam_sections
    ↓
section_items
    ↓
item_options
```

不要轻易改变核心关系。

新增功能优先考虑：

**扩展现有模型**

而不是：

**重新建立一套平行数据模型。**

* 转换

* 审计

不是直接作为前端 Runtime API。

`data/exams/index.json`

属于 Section-level 离线索引。

目前大约：

**153 条 Section-level 数据。**

它不是：

**17 套 Paper-level 数据。**

因此：

* 不作为 `/exams` 数据源
* 不强行改造成 Paper Index

## 20.2 manifest.json

用于：

* 源文件信息

* 数据统计
* 同步 / 审计

不作为正常用户页面的数据源。

页面应该让用户一眼知道：

```text

我现在看什么？

下一步做什么？
```

主要操作必须明显。

## 22.3 少操作

学习工具应该尽量减少：

* 无意义跳转

## 22.4 响应式

至少保证：

* Laptop
* Tablet
* Mobile / Narrow screen

# 23. Loading / Error / Empty 状态

所有主要数据页面必须考虑：

### Loading

数据加载过程中明确告诉用户正在加载。

### Error

请求失败时：

* 有明确错误状态
* 不显示半残页面
* 用户能够理解发生了什么

### Empty

没有数据时：

* 有明确提示
* 不显示空白页面

---

# 24. 性能原则

当前规模下不追求复杂性能优化。

优先保证：

* 页面加载稳定
* 查询合理
* 不重复请求
* 不产生明显卡顿
* 移动端基本流畅

只有出现真实性能问题后，再进行专项优化。

# 26. 工程质量要求

每个阶段完成后，根据项目实际情况执行：

```text
TypeScript typecheck
Lint
Build
Browser verification
Git diff
git diff --check
```

如果某项不适用，应由 Agent 根据项目实际情况判断，而不是机械执行。

---

# 27. Git 原则

AI Agent 不得擅自：

* push
* 强制 reset
* 删除用户文件
* 清理未知工作区文件
* 修改无关文件

尤其不得：

```text
git add .
```

来掩盖实际变更范围。

提交前必须检查：

```text
git status
git diff
git diff --check
```

确保：

**只修改本次任务真正涉及的内容。**

# 28. 与 AI Agent 的协作原则

**Goal-driven AI development**

而不是人工一步一步驱动。

---

## 28.1 AI Agent 的基本工作循环

```text
读取总需求
    ↓
读取当前 Phase

读取相关页面需求
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓
```

# 29. AI Agent 什么时候必须询问用户

正常情况下，Agent 应自行推进。

只有出现以下情况时才应该暂停：

## 29.1 产品需求冲突

例如两个正式需求文档产生矛盾。

---

## 29.2 需要产品决策

例如：

> 同一个功能存在两个完全不同且都会影响产品体验的方案，而需求没有规定。

此时询问用户。

---

## 29.3 破坏性操作

例如：

* 删除数据库表
* 删除大量数据
* 修改已有数据结构并可能造成数据损失
* 删除重要文件

必须确认。

---

## 29.4 无法安全判断

如果 Agent 无法根据：

* 总需求
* Phase
* Page Spec
* 当前代码

确定正确行为，可以暂停并询问。

除此之外，不应因为“小问题”不断打断用户。

---

# 30. AI Agent 不应该做的事情

Agent 不应该：

* 自己扩大需求
* 擅自增加功能
* 擅自修改产品方向
* 为未来需求提前实现大量代码
* 为理论安全问题无限加固
* 重复创建已有数据源
* 因为代码可以重构就随意重构
* 为了“更优雅”而改变稳定架构

原则：

> **完成需求，而不是展示自己的技术能力。**

```text

完成

        ↓

        ↓

```

> **以历年真题为核心内容，以练习、解析、错题和复习为主要学习机制的个人英语（二）长期学习系统。**

# 38. 总体设计原则

English2 的所有后续开发，都遵循以下原则：

1. **产品目标优先于技术炫技**
2. **真题数据是核心资产**
3. **数据库是运行时事实来源**
4. **不制造重复的数据源**
5. **先完成核心学习闭环**
6. **简单方案优先**
7. **避免过度工程化**
8. **安全做到够用即可**
9. **页面体验比内部复杂度更重要**
10. **AI Agent 应自主完成明确目标**
11. **需求不明确时才询问用户**
12. **不擅自扩大需求**
13. **每个阶段必须有明确验收标准**
14. **完成一个目标后自动进入下一个目标**
15. **所有重大产品决策由用户决定**

# 39. English2 的核心一句话定义

**English2 是一个以 2010–2026 年英语（二）历年真题为核心，通过真题浏览、在线练习、答案解析、错题与复习，帮助个人长期学习英语（二）的 Web 学习系统。**
